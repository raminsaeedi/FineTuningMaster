# Dataset Construction History and Methodology: From nvBench to the Frozen `dashboard_v3` Dataset

## Scope and evidential basis

This document reconstructs the repository’s documented data-construction process from the downloaded nvBench archive to the frozen `dashboard_v3` package. The reconstruction is based on the source manifests and README files, the implementation in `src/data_pipeline/`, the data and enrichment configuration files, the historical staging manifests, validation and leakage reports, and the final artifacts under `data/frozen/dashboard_v3/`. The purpose is to describe the scientific construction logic and its historical progression, rather than to reproduce operational commands or describe files that are unrelated to dataset provenance.

The final authoritative artifact is `data/frozen/dashboard_v3/`. Its manifest identifies the source as nvBench, the source version as `nvbench_large_v2`, and its status as `PASS_DASHBOARD_V3_FROZEN_READY_FOR_EXPERIMENTS`. The final package contains 1,281 training records, 264 validation records, 274 held-out test records, and a separate 40-item human-evaluation file. The repository’s `PROJECT_COMMANDS.md`, `src/config/data/dashboard_v3.yaml`, and `data/frozen/dashboard_v3/dataset_card.md` all instruct downstream experiments to use this package and not to regenerate or replace it.

The repository contains several older synthetic-data and freezing workflows, including `experiments/scripts/freeze_dataset_v2.py`. That script freezes the older synthetic `dashboard_v2` workflow and is explicitly classified as historical in `PROJECT_COMMANDS.md`; it is not the writer for the final nvBench-derived `dashboard_v3` package. Consequently, the final freeze is reconstructed here from the final manifest, hashes, reports, and freeze inputs. The current tree does not expose a separate, dedicated `dashboard_v3` freeze-writer script, which is an important provenance limitation noted again at the end of this document.

## 1. Original source data and local source registration

The primary external source is the nvBench repository recorded in `data/raw_external/nvbench/source_manifest.json`. The manifest records the repository URL as `https://github.com/TsinghuaDatabaseGroup/nvBench`, the downloaded reference as `main`, and the archive as `nvBench-main.zip`. No upstream commit was pinned. Instead, the archive’s SHA-256 digest, `2c95244aca93aaca689fc954f8ae228c6c17fd47c81e1d7b265c4191cb012e4c`, is the immutable local source identifier. The manifest records that the active README confirms the MIT license. It also records 7,247 visualization objects, 25,762 natural-language query records, 25,750 published natural-language/visualization pairs, 3,277 files, and 402,278,712 bytes.

The source README at `data/raw_external/nvbench/extracted/nvBench-main/README.md` describes the raw structure used by the extractor. At the top level, records contain a `key` and a `vis_query` collection. Within the visualization/query information, the implementation reads the visualization part, the data part, SQL and binning information, VQL, the chart label, the database identifier, the visualization object, and the natural-language queries. The visualization object includes fields such as `chart`, `x_name`, `y_name`, `x_data`, `y_data`, `classify`, and `describe`. The source chart vocabulary represented in the README includes Bar, Pie, Line, Scatter, Stacked Bar, Grouping Line, and Grouping Scatter. A single visualization object can have multiple natural-language queries; the source manifest explicitly records this relationship rather than treating the top-level object count as the record count used for modeling.

The repository also registered a separately downloaded `nvBench-2.0` archive under `data/raw_external/nvbench2/`. Its manifest records a different repository, a different archive digest, and a pending license status; its README describes a larger and modified corpus, including ambiguity injection. It is not registered as the source of the final dataset, is not used by the nvBench builder, and is absent from the final freeze inputs. The repository likewise contains an unprovisioned Quda inspection report with pending licensing and no implemented ingestion path. These sources are therefore part of the project’s source-inspection history, not stages in the provenance of `dashboard_v3`.

The database files needed to validate queries are provisioned through `src/data_pipeline/nvbench_cache.py` and `experiments/scripts/prepare_nvbench_cache.py`. The cache builder extracts the registered `databases.zip` into the rebuildable path `data/cache_external/nvbench/databases`, verifies the archive digest against the raw-source manifest, protects extraction against ZIP path traversal, and finalizes through a temporary directory. The raw archive is not modified. The cache is an execution aid for schema and result validation, not an alternative source of labels.

## 2. Source-faithful extraction and normalized records

The extraction stage is implemented primarily in `src/data_pipeline/builders/nvbench_builder.py`, `src/data_pipeline/nvbench_source.py`, and the pure parsing functions in `src/data_pipeline/nvbench_extract.py`. `nvbench_builder.py` traverses the raw `NVBench.json` in sorted-key order and emits one candidate per natural-language query, retaining a stable `query_index`. The stable identifiers distinguish a source record from a source group: `source_record_id` has the form `nvbench:{key}:query:{query_index}`, while `source_group_id` is derived from the base key after removing axis-name and sort suffixes. This group identifier is used later to prevent related records from being distributed across multiple splits.

The chart mapping is versioned in `src/config/data/nvbench_mapping.yaml`. Mapping version `v2` maps Bar to `bar`, Pie to `pie`, Line to `line`, Scatter to `scatter`, Stacked Bar to `stacked_bar`, Grouping Line to grouped `line`, and Grouping Scatter to grouped `scatter`. Unsupported labels are rejected rather than silently coerced. The same configuration records the rule-derived task mapping: for example, line is associated with trend, scatter with correlation, pie with part-to-whole, stacked bar with composition, and bar with comparison, with explicit confidence values and a default comparison fallback. The task type is not treated as an original nvBench annotation; it is recorded as rule-derived and accompanied by rule version, confidence, and evidence.

The normalized record preserves source evidence in `brief.extra.provenance`. This includes the original visualization and query information, original chart label, original query text, SQL, VQL, axis typing, KPI-selection evidence, grouping information, parsed constraints, and the raw encoding. Source-provided analytical content remains distinguishable from later derivations. In the final lineage conventions, goals, KPIs, columns, constraints, provenance, and the KPI/chart mapping are source-grounded; task inference and the KPI-selection lineage are deterministic derivations; the six presentation fields added later are LLM-generated.

The extraction code is deliberately conservative. It parses aggregate intent, nested aggregates, SELECT projections, GROUP BY terms, filters, ordering, limits, HAVING conditions, time functions, and VQL `BIN` expressions. Simple `AND` filters can be represented; `OR`, subqueries, and unparseable conditions fail closed. A single ORDER BY key is preserved with its direction; multiple or otherwise unrepresentable sorts are rejected. LIMIT/TOP and HAVING are represented separately so that a limit or condition is not accidentally attached to the wrong aggregation scope. Malformed binning and conflicting aggregate interpretations are rejected. SQL GROUP BY fields are preserved as constraints, while aggregate expressions and computed terms are not falsely promoted to physical database columns.

The natural-language text is used for narrow consistency diagnostics, not as authority to rewrite the query. The extractor’s comments document that naive keyword searches produced false positives because words such as “total” can be intensifiers and “number of” can occur with unrelated aggregates. Accordingly, required-dimension, count-threshold, and time-grain checks are narrow. A source field is not invented merely because it occurs in a natural-language request. Physical source fields, projected fields, group/filter/sort/time fields, and database types are retained; aggregate expressions are kept as aggregate evidence rather than inserted into `brief.columns`.

## 3. The initial pilots: broad acceptance exposed hidden source problems

The first pilot scripts, represented by `src/data_pipeline/nvbench_pilot.py` and `experiments/scripts/run_nvbench_pilot.py`, were useful for exposing the shape of the corpus but were not sufficient as a final construction procedure. Pilot versions 1 and 2 read 25,762 candidate query records, reported zero technical rejections, and selected 100 examples, one per source group with chart-stratified sampling. Their manifests show 20 examples for each of the five normalized chart types used in the pilot. The corresponding validation report passed structural, semantic, duplication, and leakage checks, but it also documented nine warnings: grouping fields could not be recovered for some grouped records, 95 of 100 axis types were supported by database metadata while five used heuristics, and 38 near-duplicate pairs were present as a warning.

The v1-to-v2 diagnostic in `data/staging/dashboard_v3/nvbench_pilot_v2/reports/before_after_v1_v2.md` shows why the initial “accepted” status was not equivalent to dashboard-design validity. Nineteen of the common records changed. Nine grouping fields were recovered, unresolved grouping warnings fell to zero, and the reported near-duplicate count fell from 38 to 19. The changes were not cosmetic: they altered the interpretation of grouped series and axis/KPI evidence using the database schema and profiles. The pilot therefore established that the raw record could be structurally loaded while still lacking sufficient evidence for a valid dashboard-design example.

Pilot v3 introduced the first strict candidate build and a more explicit source-preservation policy. Its manifest reports 20,986 technically accepted records and 4,776 rejected records. The rejection reasons were 3,944 unpreserved filters, 157 ambiguous nested aggregates, 260 categorical scatter axes, 236 aggregate-intent conflicts, 44 chart/query conflicts, 10 unpreserved sorts, and 125 missing group fields. The resulting 100-item selection again contained 20 examples per normalized chart type, but it was selected only after exact-goal deduplication, source-group sampling, database caps, and near-duplicate checks. Eighteen exact normalized-goal duplicates were removed from the candidate selection.

The v2-to-v3 report demonstrates the practical effect of the stricter representation. Aggregate expressions in `brief.columns` fell from 86 to zero; valid stacked-bar group fields rose from zero to 20; categorical-scatter warnings fell from eight to zero; and remaining nested-aggregate cases fell from three to zero. The report also shows that filters, sorting, time grains, and grouped evidence became represented rather than silently omitted: accepted filters rose from zero to 15, accepted sorts from zero to 43, accepted time grains from zero to 18, and grouped records from nine to 33. Duplicate findings fell to zero in the selected pilot. These changes were scientifically necessary because a training record that omits a source constraint or misrepresents a physical field teaches a model a different analytical task from the one encoded by the original SQL/VQL.

## 4. Separating source fidelity from dashboard-design validity

The quality layer was introduced because source fidelity and dashboard suitability are related but non-identical properties. This separation is explicit in `src/data_pipeline/nvbench_quality.py`: the quality layer distinguishes source-valid records from records that are also appropriate for dashboard-design supervision. A source record can therefore remain useful as provenance while being excluded from the high-confidence training pool because its chart, KPI, identifier use, grouping, or constraint scope is unsuitable.

Tier A denotes a high-confidence positive candidate. Tier B denotes a source-faithful record that is uncertain or unsuitable for the intended dashboard-design task but remains diagnostically informative. Tier C denotes a severe contradiction. A record is not promoted to Tier A when it has a mandatory failure, even if a superficial schema check passes. The final quality configuration is `src/config/data/nvbench_quality_rules.yaml` with rule version `nvbench_quality_v6`; the implementation reports the corresponding `QUALITY_RULE_VERSION` as `nvbench_quality_v6`.

The quality score combines source fidelity, KPI validity, chart suitability, constraint completeness, and database-profile support. The configured weights are 30, 20, 25, 15, and 10 respectively, and Tier A requires a score of at least 90. The score is a prioritization and admission mechanism, not a claim that the source is human-verified ground truth. Severe contradictions, such as an identifier aggregation combined with an aggregate/query conflict, are eligible for Tier C treatment. Less severe uncertainty can remain Tier B without being rewritten.

### Identifier detection and KPI suitability

Identifier detection is implemented in `src/data_pipeline/nvbench_identifier.py`. A field name alone is never sufficient strong evidence because names such as “id” or “code” can be ambiguous. Strong evidence comes from primary-key, foreign-key, or unique-index metadata, a sufficiently high unique ratio with enough distinct values, repeated numeric entity-reference patterns, and related statistical evidence. The implemented rule version is `nvbench_identifier_v3`. The database profiler in `src/data_pipeline/nvbench_profile.py` caches schema information and full-table statistics including row counts, null and distinct ratios, uniqueness, numeric ratios, ranges, sign counts, and examples. SQL result profiles are read-only and capped at 1,000 rows; raw result values are not persisted.

KPI selection is deliberately constrained. An explicit aggregate is retained when it is unambiguous; with two aggregates, the y-side aggregate is primary while both aggregates remain represented. When no aggregate is available, the selector searches for a numeric, non-identifier-like measure, preferring the y-side evidence when appropriate. COUNT is accepted as a meaningful measure only when the query expresses entity-count intent, such as COUNT(*) or counting an entity or categorical field. SUM, AVG, MIN, and MAX over a strong identifier are demoted with reason codes such as `identifier_as_measure`, `meaningless_identifier_aggregation`, `invalid_identifier_aggregation`, or `wrong_kpi`. If a source y field is retained for fidelity but no valid KPI can be established, the record is not silently repaired; its quality tier reflects the deficiency.

### Chart suitability

Chart checks assess whether the source-supported fields and query result can plausibly support the source chart. Bar charts require measure evidence and are blocked when a strong identifier is used as the measure. Line charts require a numeric measure and an ordered x-axis, supported by a datetime field, explicit time grain, or source ordering; an unordered categorical x-axis is insufficient. Pie charts are limited to at most eight categories, reject identifier-like categories and negative measure bases, and accept additive COUNT or SUM aggregation. AVG, MIN, and MAX are non-additive for the pie policy and are demoted with `pie_non_additive_kpi`; a non-aggregate percentage over independent temporal x-values is not treated as part-to-whole evidence.

Scatter charts require independently typed numeric x and y measures. Identifier axes are rejected, non-aggregate axes need sufficient distinctness, and aggregate axes require a valid non-aggregate SQL grouping or source-backed VQL binning. The executed query result is profiled at the result level, not merely at the base-table level: the result must contain at least two paired numeric rows with sufficient distinctness in x, y, and pairs. This prevents a chart from being called a valid scatter plot solely because its underlying table contains many rows. Grouped and stacked-bar charts require an unambiguous group field, bounded group cardinality, and a non-identifier grouping dimension.

### Constraint preservation and source consistency

The quality checks require explicit source constraints to survive normalization. Valid SQL GROUP BY fields must appear in the normalized representation. Explicit time functions or grouped datetime x-fields must yield a time-grain record. Required grouping dimensions, aggregate conditions, filters, sort order, LIMIT/TOP, and HAVING conditions are checked for scope and representability. An ORDER BY or LIMIT that applies to a different aggregation level is not treated as an incidental detail. VQL `BIN` is retained as source-backed visual grouping; it is not converted into fabricated SQL GROUP BY evidence. Narrow natural-language diagnostics check dimensions, count thresholds, and time grains against the query without rewriting either source.

## 5. Quality-filtered pilot progression

Pilot v4 applied quality tiering to the v3 technical pool. Its manifest reports 20,986 technically valid records, of which 13,896 were Tier A, 7,071 Tier B, and 19 Tier C. The selected pilot contained 95 records and all selected records were Tier A, but it was explicitly partial because the target of 20 scatter records could not be met; 15 scatter records were selected and the other chart types contributed 20 each. The v3-to-v4 report records the problems removed by this quality constraint: identifier-as-measure cases fell from 31 to zero, meaningless KPI cases from 29 to zero, chart-inappropriate cases from 37 to zero, source conflicts from two to zero, invalid scatter cases from 19 to zero, and the reported line, stacked-bar, and bar-specific failures also fell to zero in the selected sample. This shows why the original balanced pilot was insufficient: chart balance without semantic suitability would have required retaining records that the quality layer considered invalid dashboard examples.

Pilot v5 used a revised quality rule set. The manifest reports 13,044 Tier A, 7,923 Tier B, and 19 Tier C records in the same 20,986-record technical pool. The selection failed its requested balanced target because only ten scatter records were available after the Tier-A and deduplication constraints. The reported dominant failures included identifier-as-measure and meaningless identifier aggregation, insufficient database or measure evidence, continuous identifier use, missing grouping or time evidence, and low-variation or identifier-like scatter axes. Relative to v4, the diagnostic report shows that KPI conflicts fell from five to zero, missing time grains from seven to zero, missing grouping from four to zero, and the selected score minimum rose from 65 to 95. The result was scientifically preferable to filling the missing quota from Tier B: the manifest records the shortage rather than relaxing the admission criterion.

Pilot v6 selected 100 records without a Tier-B fallback, but retained the source-driven imbalance. Its manifest records 23 bar, 23 line, 22 pie, 22 stacked-bar, and 10 scatter examples. The reason given is that only 43 Tier-A scatter candidates spanning 13 unique source groups remained before the final selection constraints. Exact-goal duplicates and near duplicates were removed, and the validation report records no duplicate IDs, duplicate briefs, duplicate goals, near duplicates, leakage, KPI/SQL conflicts, missing time/group evidence, identifier measures, or invalid scatter cases. Pilot v6 is therefore the final pilot evidence for a quality-constrained, deliberately unbalanced selection rather than an artificially balanced but lower-validity sample.

## 6. Rebuilding the full Tier-A pool and correcting the large-dataset rules

The later quality-pool rebuilds are distinct from the initial v3 technical pool. `data/staging/dashboard_v3/nvbench_quality_pool_final/manifest.json` reports 21,244 technically valid records under rule version `nvbench_quality_v5`, with 11,658 Tier A, 9,557 Tier B, and 29 Tier C. The subsequent `data/staging/dashboard_v3/nvbench_quality_pool_final_v2/manifest.json` keeps 21,244 technically valid records but applies rule version `nvbench_quality_v6`, yielding 12,147 Tier A, 9,064 Tier B, and 33 Tier C. The final large-dataset build references the latter pool through `data/staging/dashboard_v3/nvbench_large_v2/quality_pool_reference.json`. The repository does not provide a complete row-level reconciliation between the initial 20,986-record v3 pool and the later 21,244-record rebuild, so the numerical difference should be treated as a documented rebuild boundary rather than as a silently inferred addition or deletion history.

The large-dataset selection logic is implemented in `src/data_pipeline/nvbench_large_v1.py` and reused by the later builder. It consumes Tier-A records only and does not relax the quality rules to meet a target. It limits source-group multiplicity to at most two records, admits a second record from a group only when its wording is sufficiently different and its semantic signature differs, and uses exact normalized-goal, fingerprint, and near-duplicate checks. The near-duplicate threshold is character 3-gram Jaccard similarity of 0.8. Database caps and leakage exclusions are applied during availability and admission calculations. For chart allocation, every survivable scatter record is considered first because scatter is the scarce class; the non-scatter quota logic then aims for a 40/20/20/20 remainder while redistributing deficits only when a chart pool is exhausted. A bar cap prevents one class from filling the entire selected corpus. These are selection constraints, not quality relaxations.

The historical large v1 build reached 1,819 records, passed its minimum of 1,800, retained 1,647 records from the preceding selection, and used 172 replacements. It is explicitly retained as a historical intermediate. The rule-repair and large-v2 reports document why it was not treated as final. The repair summary records 1,197 promotions, 708 demotions, and 295 affected source groups; changed reason counts include 634 goal mismatches, 585 wrong-KPI cases, 65 query-aggregation conflicts, 41 missing-grouping cases, 26 constraint-scope errors, and additional identifier, scatter, and invalid-group-by corrections. The final large-v2 manifest records 1,819 selected records, retaining 1,667 previous records and replacing 152.

The large-v2 rule changes were informed by both deterministic checks and targeted inspection. `data/staging/dashboard_v3/nvbench_large_v2/reports/pre_repair_verification.md` states that three AI-flagged records were independently checked against raw JSON, rendered source information, SQL, VQL, and SQLite schemas/profiles. The report identifies a confirmed identifier aggregation in `nvbench:1048@x_name@DESC:query:0`, where a VARCHAR `card_number` field with 15 unique numeric-looking values was summed even though the query omitted the relevant entity identifiers. It identifies a valid source-backed VQL weekday bin in `nvbench:2780:query:1`, but an incompatible SQL aggregation and top-five row scope; the correct action was a constraint-scope and goal mismatch demotion, not merely a missing SQL GROUP BY label. It also identifies an invalid aggregate expression used as a GROUP BY key and missing observation unit in `nvbench:3257:query:3`, requiring demotion for invalid grouping and insufficient scatter observations. The report treats these AI diagnostics as prompts for independent verification, not as human gold labels. It also states that the underlying AI audit files were absent and that the provenance of the closest R1 template could not be established.

The final large-v2 validation report passes structural, semantic, duplicate, leakage, and source-preservation checks. It confirms that normalized chart types match the original labels, grouping information and classification are preserved, task types are rule-derived, aggregate axes are numeric, non-aggregate types agree with the database where checked, y-fields are not forced to numeric without evidence, KPI policy is consistent, and no LLM-generated fields occur at this phase. The large-v2 manifest records the final split counts as 1,281 train, 264 validation, and 274 test. Source groups are disjoint across the three splits, with 784, 167, and 167 unique groups respectively. The held-out test is therefore an in-domain nvBench test set rather than a fully external benchmark.

The final large-v2 chart distribution is 1,379 bar, 109 line, 242 pie, 13 scatter, and 76 stacked-bar records. The corresponding task distribution in the frozen validation report is 1,379 comparison, 109 trend, 242 part-to-whole, 13 correlation, and 76 composition. The imbalance is a consequence of the surviving Tier-A supply and the source-group, deduplication, database-cap, and leakage constraints. In particular, scatter remained scarce; the pipeline records this scarcity rather than manufacturing additional scatter examples.

## 7. Deduplication, leakage control, and split preservation

Deduplication operates at several levels because a single identifier check is not sufficient for this source. The pipeline checks exact item IDs, source-record IDs, source groups, normalized goals, brief fingerprints, and character 3-gram near duplicates. Source groups are formed before split assignment and before chart stratification. The large-dataset policy permits at most two records per source group only when their semantic signatures differ; this preserves limited within-source variation without allowing a source family to dominate a split.

Leakage checks compare training, validation, test, human-evaluation, and other evaluation artifacts using item IDs, source-record IDs, source groups, brief fingerprints, and near-duplicate similarity where applicable. The large-v2 split algorithm is deterministic with seed 42 and assigns whole source groups to train, validation, or test. The nominal 70/15/15 proportions are subordinate to group integrity; the actual final proportions are approximately 70.42%, 14.51%, and 15.06%. The final `data/frozen/dashboard_v3/reports/leakage_report.json` reports no train/test, validation/test, train/validation source-group, or human-evaluation overlap. The final validation report also records zero duplicate IDs and zero duplicate brief fingerprints.

The 40 human-evaluation items are selected from the held-out test split using a deterministic, coverage-oriented sampler. They remain separate from the trainable records and are copied into the final frozen package as a CSV with blank review fields before human review. They are not used as enrichment inputs, prompt-selection examples, or hyperparameter-selection data. This distinction is essential: the human-evaluation file is an evaluation instrument, not an additional training split.

## 8. LLM enrichment as a constrained presentation layer

After the analytical selection was complete, the project added presentation-oriented fields through the Phase-3 enrichment workflow. The implementation is in `src/data_pipeline/enrichment.py` and `src/data_pipeline/enrichment_full.py`, with execution wrappers in `experiments/scripts/run_enrichment_sample.py`, `run_enrichment_full.py`, and `run_enrichment_targeted_retry.py`. The full run reads only the large-v2 training and validation records. `src/data_pipeline/enrichment_full.py` explicitly rejects input paths matching test or human-evaluation patterns, and the full-run manifest records that zero test records and zero human-evaluation items were processed.

The enrichment contract permits the model to write exactly six fields: `users`, `context_summary`, `layout`, `styling`, `interactions`, and `rationales`. The analytical and source-backed portions of each record are immutable, including the item ID, provenance, goals, KPI, chart type, task and encoding information, alternatives, filters, sorting, limits, grouping, time grain, raw columns and types, quality tier and score, and split. The code computes an immutable projection and SHA-256 fingerprint before and after enrichment; a change to an immutable field is rejected with `immutable_source_field_changed`.

The enrichment prompt supplies fixed source facts and allowed source fields. Validation rejects invented KPIs, invented chart types, invented business numbers, context conflicts, unsupported interaction types, interactions that refer to fields outside the source encoding/columns, and rationales that do not mention the task, selected chart, and encoded fields. The strict Pydantic payload forbids extra fields. The trusted application code, rather than the LLM, merges only the six permitted fields and marks their lineage as `llm_generated`. The provider reads its secret only from the environment variable `ENRICHMENT_API_KEY`; secrets, raw API responses, caches, and temporary generations are excluded from the final frozen package.

The enrichment history has three relevant checkpoints. A technical ten-record sample passed with all ten records accepted. The 30-record pilot contained 29 accepted and one rejected record; the pilot rejection was a rationale disagreement with the task, chart, or encoding. The full run then processed 1,545 records, comprising 1,281 train and 264 validation records. It produced 1,534 accepted records and 11 rejected records on the first pass, with a schema-valid rate of 100%, no immutable-field violations, 943 API calls, 617 cache hits, and 15 retries. Its configured generation temperature was 0.0, with the model recorded as `deepseek-v4-flash-sovereign` and requested reasoning effort `xhigh`.

The targeted retry workflow did not recall accepted records. It resolved ten of the 11 rejected cases through offline revalidation and resolved the remaining case after one additional API call. It left zero permanently rejected records and reconciled to all 1,545 expected train/validation records. The pre-freeze audit reports complete enrichment fields for 1,545 of 1,545 records, zero semantic/content-validator failures, zero immutable violations, and byte-equivalent analytical fields before and after enrichment. The audit also records that the record-level immutable fingerprint metadata was blank on 1,534 full-run records; the pre-freeze process recomputed this metadata without changing source-backed or enriched values. This was metadata normalization, not a change to the dataset’s analytical content.

Human review was used as a limited enrichment gate, not as a source-quality gold-labeling exercise. The R1 enrichment audit covered 30 records, accepted 29, rejected one, and met the configured minimum of 27 accepted records. There were no incomplete review fields and no flagged immutable violations; one placeholder value was recorded. The final manifest therefore documents the human R1 result, while still marking all six presentation fields as LLM-generated and not gold. This is materially different from treating the 30-item review as an independent human annotation for the entire dataset.

## 9. The hybrid staging branch and convergence on the final source scope

The repository also contains `src/data_pipeline/hybrid_dataset.py` and `data/staging/dashboard_v3/hybrid_dataset_v1/`. That staging package combined 1,281 enriched nvBench training records with 18 deterministic synthetic records and 264 enriched nvBench validation records with three synthetic records, for totals of 1,299 and 267. Its manifest reports passing schema, provenance, split, cross-source deduplication, and leakage checks. Synthetic records were tagged as `synthetic_generated`, were not treated as nvBench or human gold, and were excluded when they collided with source-grounded nvBench records.

The hybrid package is not, however, the final `dashboard_v3` freeze. The final manifest’s freeze inputs point to `data/staging/enrichment/full_train_val_v1/final/train_accepted_final.jsonl` and `val_accepted_final.jsonl`, together with the un-enriched large-v2 test and human-evaluation artifacts; it does not point to `hybrid_dataset_v1`. The final counts are consequently 1,281 and 264 rather than 1,299 and 267. The repository documents the existence and validation of the hybrid candidate but does not provide a separate narrative explaining the final decision to omit its 21 synthetic records. The evidence-supported conclusion is therefore that the final frozen scope is nvBench-only, while the hybrid package remains a validated but non-authoritative staging branch.

## 10. Final freeze, validation, and provenance

The final package was frozen at `2026-08-07T13:37:12.618116+00:00`, according to `data/frozen/dashboard_v3/manifest.json`. The resulting package is therefore not merely a directory of JSONL files but a versioned, hashed, lineage-labelled dataset with an explicit evaluation boundary.

## 12. Scientific limitations and caveats

First, the upstream source is an archive of the `main` branch without an upstream commit pin. The archive digest is a strong local integrity identifier, but it does not provide the same reproducibility guarantee as a commit hash tied to a released upstream version. The raw source manifest and archive digest should therefore accompany any external reproduction.

Second, source fidelity is not equivalent to semantic truth. The pipeline preserves original SQL, VQL, chart labels, encodings, and constraints, but the quality reports demonstrate that some source records contain identifier aggregations, invalid grouping expressions, incompatible limits, or chart/query conflicts. The construction procedure addresses this by rejecting or demoting records; it does not establish that every retained nvBench query is a human-verified description of a meaningful business dashboard.

Third, several judgments depend on database metadata and deterministic heuristics. Identifier detection uses primary/foreign-key information, uniqueness and distinctness thresholds, name patterns, and result profiles. Axis typing can fall back to heuristics when database metadata is unavailable, although final reports record the provenance of such decisions. Quality tiers and scores are therefore rule-based operational definitions of suitability, not universal measures of chart quality.

Fourth, the final test set is in-domain and source-group-disjoint, not an external benchmark. The separate literature-based or real-brief evaluation artifacts are maintained outside the trainable package. The final chart distribution is strongly bar-dominated and contains only 13 scatter records because the quality, source-group, deduplication, database, and leakage constraints limited the available supply. Aggregate performance results should account for this class imbalance and scarcity.

Fifth, the six presentation fields are LLM-generated design annotations. Automated validators constrain them, and a 30-record R1 enrichment review passed its acceptance gate, but these fields are not nvBench gold, independent human gold, or expert gold. The final package should not be described as human-annotated dashboard-design ground truth. In particular, the small R1 enrichment audit does not validate every possible user description, layout choice, styling choice, interaction, or rationale in the 1,545 enriched records.

Sixth, the repository records an AI-assisted source-rule repair process but not a complete audit trail for it. The three records documented in `pre_repair_verification.md` were independently checked, and the resulting rule changes are summarized. The report also states that the referenced AI audit files were absent and that the provenance of the closest source-quality R1 template could not be established. A complete historical reconstruction of every AI suggestion and every human source-quality decision is therefore not possible from the current repository.

Seventh, the hybrid staging package demonstrates a possible multi-source construction but is not the final freeze input. The repository does not explain in a dedicated final-decision report why the validated 18 train and three validation synthetic records were omitted from `dashboard_v3`. The final manifest is unambiguous about the selected inputs, so the omission is established; its motivation is not.

Finally, the later quality-pool rebuild reports 21,244 technically valid records, whereas the first strict v3 candidate report records 20,986. The repository preserves both histories but does not provide a complete row-level reconciliation for the 258-record difference. This should be reported as a rebuild boundary in a thesis rather than presented as a fully traceable per-record transition unless the missing reconciliation is recovered.
